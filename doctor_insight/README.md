# doctor_insight：MR日報から皮膚科医の評価とネックを定量化する試作

MR日報の自由記載から、皮膚科医ごとに自社品への評価とネックを取り出して数値にします。
そのうえで、医師をカテゴリに分け、次の四半期を予測し、説明会などの施策の効果を推定します。
ここまでを通して動かす試作です。

**すべて架空のデータで動きます。** 医師、施設、製品（製品A〜C）は架空で、実在のものとは関係ありません。
設計の考え方は、共有ドキュメントの「分析の設計書」タブにあります。

## 動かし方

```bash
pip install -r requirements.txt
python -m doctor_insight.run_demo            # ルールで抽出する（GPUなしで動く、約10秒）
```

結果は `outputs/report.md` と `outputs/*.csv` に書き出します。

社内のGPUでLLMを動かして抽出する場合は、まずOpenAI互換のサーバーを社内に立てます。

```bash
vllm serve tokyotech-llm/Medical-Qwen3-Swallow-8B --port 8000
python -m doctor_insight.run_demo --llm-base-url http://localhost:8000/v1 \
    --llm-model tokyotech-llm/Medical-Qwen3-Swallow-8B --llm-limit 2000
```

日報のデータは社外に出ません。モデルのライセンスは、使う前にHugging Faceのモデルカードで確認してください。

## 構成

| ファイル | 役割 | 設計書の段階 |
| --- | --- | --- |
| `schema.py` | 日報1件から抽出する項目（話題、評価、処方の段階、ネック、患者の話題の有無、根拠の文） | 抽出する項目 |
| `simulate.py` | 架空の日報、施設の売上、製品Aの症例登録を作る。医師の隠れた特性とMRの書き方の癖を持つ | — |
| `topics.py` | トピック抽出で、日報にどんな観点があるかを洗い出す（文意知に近い考え方） | フェーズ1 |
| `extract_llm.py` | 社内のLLMで項目を抽出する。出力をJSONスキーマで制約し、根拠の文が日報にあるかを確かめる | フェーズ2 |
| `extract_rules.py` | キーワードのルールで抽出する仮の抽出器。LLMと比べる基準 | フェーズ2 |
| `evaluate.py` | 人手のラベルと比べて、一致率（κ）、適合率、再現率を測る | 検証 |
| `features.py` | 医師×製品×四半期の特徴量。MRの書き方の補正、縮小推定、他の自社品からの特性 | 医師のカテゴリ分け |
| `segment.py` | ルールによるカテゴリと、クラスタリング | 医師のカテゴリ分け |
| `predict.py` | 時間で分けた評価。単純な予測と比べる | 将来予測 |
| `uplift.py` | 説明会の効果の推定（単純な比較、傾向スコアの重み付け、医師ごとの効果） | 「こうすれば変えられる」 |
| `run_demo.py` | 全体を通して動かす | — |

## 架空データでの結果の読み方

結果は、手法がどう動くかを確かめるためのものです。実データでの精度や効果を示すものではありません。

- **抽出の精度は、実データより高く出ます。** 架空の日報は決まった文型から作っているため、ルールでもほぼ正しく抽出できます。
  実際の日報は、省略や言い換え、社内の略語が多いはずです。
  必ず実際の日報に人手でラベルを付け、`evaluate.py` で測り直してください。
- **予測の改善は小さいです。** 自由記載の評価やネック、他の自社品の情報を加えると、製品Aの症例登録の予測は少し良くなりました。
  一方、新製品Cの段階の予測は良くなりませんでした。
  これは「自由記載を足せば必ず良くなるわけではない」ことの例です。実データでも、まず単純な予測と比べてください。
- **施策の効果は、補正しても大きく見積もられます。** 架空データでは、説明会の本当の効果が分かります。
  単純な比較も、日報の特徴量で補正した推定も、本当の効果より大きくなりました。
  日報に書かれていない違い（もともとの関心の高さなど）が残るためです。推定は仮説として扱い、訪問計画で試して確かめてください。

## 実データに置き換えるとき

1. `simulate.py` の代わりに、次の表を社内のデータから読み込みます。
   - 日報：`report_id, doctor_id, facility_id, mr_id, product, quarter, q_index, text`
   - 説明会などへの参加：`doctor_id, product, q_index, seminar`（参加記録から作る）
   - 施設の売上：`facility_id, product, quarter, sales`
   - 症例登録：`doctor_id, product, quarter, new_registrations`（**分析に使ってよいか、先に確認すること**）
2. 実データには答えがないため、`states` の `true_*` と `p_up_*` の列は使えません。
   `run_demo.py` の該当部分（施策の効果の「本当の効果」の行など）は外します。
3. 300〜500件の日報に2人以上で人手のラベルを付け、`evaluate.py` で抽出の精度を測ります。
4. 患者の話題を含む日報（`mentions_patient`）は、分析に使う前に除くか、内容を消します。

## 注意

- 日報には医師の個人情報が含まれます。LLMの入力、出力、ログの保管場所とアクセスできる人を決めてから使ってください。
- 医師のカテゴリや予測をMRの評価に直接使うと、日報の書き方が変わり、指標が壊れる恐れがあります。
- 施策の提案は、社内で承認された資材と適応の範囲に限ってください。
