# doctor_insight：MR日報から皮膚科医の評価とネックを定量化する試作

MR日報の自由記載から、皮膚科医ごとに自社品への評価とネックを取り出して数値にします。
そのうえで、医師をカテゴリに分け、次の四半期を予測し、説明会などの施策の効果を推定します。
ここまでを通して動かす試作です。

**すべて架空のデータで動きます。** 医師、施設、製品（製品A〜C）は架空で、実在のものとは関係ありません。
設計の考え方は、共有ドキュメントの「分析の設計書」タブにあります。

## 動かし方

```bash
pip install -r requirements.txt
python -m doctor_insight.run_demo            # ルールで抽出する（GPUなしで動く、約10秒）
```

結果は `outputs/report.md` と `outputs/*.csv` に書き出します。

社内のGPUでLLMを動かして抽出する場合は、まずOpenAI互換のサーバーを社内に立てます。

```bash
vllm serve tokyotech-llm/Medical-Qwen3-Swallow-8B --port 8000
python -m doctor_insight.run_demo --llm-base-url http://localhost:8000/v1 \
    --llm-model tokyotech-llm/Medical-Qwen3-Swallow-8B --llm-limit 2000
```

日報のデータは社外に出ません。モデルのライセンスは、使う前にHugging Faceのモデルカードで確認してください。

## 構成

| ファイル | 役割 | 設計書の段階 |
| --- | --- | --- |
| `schema.py` | 日報1件から抽出する項目（話題、評価、処方の段階、ネック、患者の話題の有無、根拠の文） | 抽出する項目 |
| `simulate.py` | 架空の日報、施設の売上、製品Aの症例登録を作る。医師の隠れた特性とMRの書き方の癖を持つ | — |
| `topics.py` | トピック抽出で、日報にどんな観点があるかを洗い出す（文意知に近い考え方） | フェーズ1 |
| `extract_llm.py` | 社内のLLMで項目を抽出する。出力をJSONスキーマで制約し、根拠の文が日報にあるかを確かめる | フェーズ2 |
| `extract_rules.py` | キーワードのルールで抽出する仮の抽出器。LLMと比べる基準 | フェーズ2 |
| `evaluate.py` | 人手のラベルと比べて、一致率（κ）、適合率、再現率を測る | 検証 |
| `features.py` | 医師×製品×四半期の特徴量。MRの書き方の補正、縮小推定、他の自社品からの特性 | 医師のカテゴリ分け |
| `segment.py` | ルールによるカテゴリと、クラスタリング | 医師のカテゴリ分け |
| `predict.py` | 時間で分けた評価。単純な予測と比べる | 将来予測 |
| `uplift.py` | 説明会の効果の推定（単純な比較、傾向スコアの重み付け、医師ごとの効果） | 「こうすれば変えられる」 |
| `run_demo.py` | 全体を通して動かす | — |

## 架空データでの結果の読み方

結果は、手法がどう動くかを確かめるためのものです。実データでの精度や効果を示すものではありません。
以下は seed 0〜2 の3回の結果です（`--seed` で変えられます）。

- **ルールでの評価・段階・ネックの抽出の精度（100%）には意味がありません。** 架空の日報は約190種類の決まった文から作っており、ルールもその文に合わせて書いたため、ほぼ完全に抽出できます（話題は100%ではありません）。
  実際の日報は、省略や言い換え、社内の略語が多いはずです。
  必ず実際の日報に人手でラベルを付け、`evaluate.py` で測り直してください。
- **この架空データでは、自由記載を足しても予測は良くなりませんでした。**
  - 製品Aの症例登録の予測は、基準（日報上の段階、段階が書かれてからの経過、面談回数）だけでAUCが約0.82でした。
  - 自由記載の評価・ネックや他の自社品の情報を足した場合の差は、−0.027〜0.000でした。95%区間が0を含まないものは、どれも悪化の方向でした。
  - この区間は評価用の行だけを再標本化したもので、モデルの学習し直しを含まないため、不確かさを小さめに見積もっています。
  - この架空データでは、登録が本当の段階だけで決まるため、自由記載に追加の情報がないからです。
  - 実データで同じ結果なら、自由記載の解析よりも、入力の構造化や外部データに力を回すべきという判断になります。まず単純な予測と比べてください。
- **新製品Cの段階の予測（練習用）は、判断できるだけの件数がありません。** 古い段階を引き継いだだけの行を除くと、評価の行は240〜270件しか残らず、AUCの差の95%区間は±0.1以上と広くなりました。日報上の段階は説明変数も結果も同じMRの記述なので、もともと予測力の判断には使いません。
- **施策の効果は、日報の特徴量で補正しても大きく見積もられました。**
  - 本当の効果は0.16〜0.17、単純な比較は0.20〜0.22、補正後は0.19〜0.22でした。日報の特徴量での補正は、偏りをほとんど減らしませんでした。
  - 補正後の95%区間は、3回のうち2回で本当の効果を含みませんでした。ただし、この3回は偏りが大きく出る側に寄っていました。
    コードのレビューで13回分を確かめたところ、単純な比較の偏りは平均で約+0.02（0.172〜0.218）でした。
    本当の傾向スコアで重み付けしても、seed 0〜2では本当の効果より大きく出ており、ずれの一部は標本の揺れによるものです。
  - 偏りの原因の1つは、日報に書かれない「新薬を早く採用する傾向」が、説明会への参加と段階の上がりやすさの両方に効いていることです。
  - 区間が本当の効果を含むかどうかは、3回では判断できません。多くのseedで確かめる必要があります。
  - 推定は試す施策を選ぶためだけに使い、訪問計画で確かめてください。
- **医師の特性ごとの効果の向きは出ましたが、医師1人ずつの効果は当たりません。**
  - 他の自社品の日報から作った「エビデンス重視」の指標は、本当の特性と0.38〜0.41の相関でした。
  - この指標で3群に分けると、効果の大小の順番は本当の効果と一致しました。
  - 一方、医師1人ずつの効果の推定と本当の効果の相関は0.02〜0.15でした。個別の医師に施策を割り当てる根拠には使えません。

## 試作の限界（コードのレビューで分かったこと）

- **MRの書き方の補正は簡易版です。** MRごとの平均の差を引くだけで、担当する医師の違いも一部吸収してしまいます。架空データでは、補正の効果は小さいものでした。実データでは、医師とMRの交差ランダム効果モデルに置き換えてください。
- **学習期間の中では、少し先の日報を使っています。** MRの補正と製品の平均は2024Q3までの日報で一度だけ計算するため、それより前の学習用の行も、その後の日報の影響を受けます。評価用の行（2025年）には影響しません（テストで確かめています）。厳密にするには、四半期ごとに過去の日報だけで計算し直します。
- **他の自社品の特徴量は、製品×四半期あたりの率にしています。** 件数のままだと、窓が埋まる期間の始めや新製品の発売で値が増え続け、学習と評価で分布がずれるためです。窓が埋まらない2023年の最初の3四半期は学習に使いません。他の自社品への評価の平均（`other_att_mean`）は、医師の段階が上がるにつれて評価も上がるため、時間とともに少し上がります。
- **直近4四半期の窓は、行の数で数えています。** 四半期が欠けたデータでは窓が長くなるため、先に四半期を埋めてください。
- **LLMでの抽出は、実際のサーバーではまだ試していません。** 思考の過程（`<think>`）やコードの囲みを取り除く処理、根拠の文の確認、再試行は、偽のクライアントでだけ確かめています。`strict` な構造化出力への対応はサーバーによって違うため、最初に少数の日報で確かめてください。
- **患者の話題の検知は、決まった言い回しに頼っています。** 「70代の」「患者さんで」などの言い回しで検知しているため、言い回しが違う患者の話題は見落とします。実データでは、患者の話題の検知そのものの精度も測ってください。

## 実データに置き換えるとき

1. `simulate.py` の代わりに、次の表を社内のデータから読み込みます。
   - 日報：`report_id, doctor_id, facility_id, mr_id, product, quarter, q_index, text`
   - 説明会などへの参加：`doctor_id, product, q_index, seminar`（参加記録から作る）
   - 施設の売上：`facility_id, product, quarter, sales`
   - 症例登録：`doctor_id, product, quarter, new_registrations`（**分析に使ってよいか、先に確認すること**）
2. 実データには答えがないため、`states` の `true_*`、`p_up_*`、`can_move`、`moved_up_next` の列は使えません。
   施策の効果の推定では、対象の条件（まだ段階が上がりうる医師）と結果を、日報上の段階や症例登録から作り直します。
   「本当の効果」の行と、本当の特性との相関の表示は外します。
3. 300〜500件の日報に2人以上で人手のラベルを付け、`evaluate.py` で抽出の精度を測ります。
4. 患者の話題を含む日報（`mentions_patient`）は、分析に使う前に除くか、内容を消します。

## 注意

- 日報には医師の個人情報が含まれます。LLMの入力、出力、ログの保管場所とアクセスできる人を決めてから使ってください。
- 医師のカテゴリや予測をMRの評価に直接使うと、日報の書き方が変わり、指標が壊れる恐れがあります。
- 施策の提案は、社内で承認された資材と適応の範囲に限ってください。
